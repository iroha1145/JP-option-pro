## 1. J-Quants が実際に返す列（推測ではなく実測）

`/markets/short-sale-report` の一括配信 CSV を 1 本開いて確認した列:

```
DiscDate  CalcDate  Code  SSName  SSAddr  DICName  DICAddr  FundName
ShrtPosToSO  ShrtPosShares  ShrtPosUnits  PrevRptDate  PrevRptRatio  Notes
```

| 列 | 保存先 | 使い道 |
| --- | --- | --- |
| `CalcDate` | `position_date` | 残高の基準日。**これで信号を立ててはいけない** |
| `DiscDate` | `published_date` | 市場が知りうる日。点時セマンティクスの起点 |
| `SSName` | `raw_holder_name` | 機関実体の正規化入力 |
| `SSAddr` | `holder_address` | 同名別法人の切り分け |
| `DICName` / `DICAddr` | `manager_name` / `manager_address` | 投資一任契約の相手方（報告主体 ≠ 運用者の切り分け） |
| `FundName` | `investment_fund_name` | 実データの 99.3% が `-`。残り 2,094 件に実名 |
| `ShrtPosToSO` | `short_ratio` | 発行済株式数に対する比率 |
| `ShrtPosShares` | `short_shares` | 株数 |
| `PrevRptRatio` | `previous_ratio` | 前回報告値。変化幅はここから取る |
| `Notes` | `notes` | 下記参照 |

`Notes` の実測分布（279,738 件時点）:

| 値 | 件数 | 意味 |
| --- | --- | --- |
| `-` | 237,192 | 特記なし |
| `顧客取引に係るヘッジポジション…を含む` | 40,753 | **顧客取引のヘッジ**。方向性の売り建てと同じには読めない |
| `Below the threshold` | 486 | 閾値割れの最終報告 |
| `変更` / `Change in holding percentage` | 468 | 訂正 |
| `報告遅延のため` | 210 | 遅延報告 |

ヘッジ明記の建玉には `is_hedge_disclosed` を立て、画面にも「含对冲持仓」と出す。

**発行済株式数は `securities` に無い。** 比率と株数は報告に両方入っているので、
指標の計算には要らない。株数を出来高で正規化する（ADV20）方針にしたのはこのため。

### 開示ラグ（実測、10 年 140 万件）

| 公開日 − 仓位日 | 件数（2025-06 以降の 28 万件で計測） |
| --- | --- |
| 1 日 | 45,434 |
| 2 日 | 124,546 |
| 3 日 | 16,425 |
| 4 日 | 75,064 |
| 5 日 | 13,999 |
| 6–7 日 | 3,901 |

最頻は 2 日、次が 4 日。10 年ぶんを入れると **最大 13 日** の例も出る
（3905 だけで 1/2/3/4/5/6/7/9/10/12/13 日の全部が観測される）。
`position_date` を信号日に使うと、その日数ぶんの未来情報を過去に流し込む
ことになる。`effective_trade_date` は「**公開日より厳密に後**の最初の営業日」
—— JPX の公表は当日 16:00 締めの受付分（取引終了後）なので、公開日当日の
終値は「その情報で取れた値段」ではない（第十三轮 P0-2）。

### 訂正

同じ `(code, calc_date, holder)` で `DiscDate` が複数あるものが訂正。実測 212 組。
元の報告は消さずに残し、後から出たほうに `correction_status = correction` を付ける。
断面は「締切以前で最も新しい公開日」を採るので、訂正が公開される前の断面に
訂正後の値は漏れない。

## 2. 「公开可见机构空头」が総空头ではない理由

報告義務はイベント駆動:

* 0.5% を超えたときに義務が生じる
* 以後 0.1% 以上動くたびに報告
* 0.5% を割ったら **最終報告を 1 本**出して義務が消える

したがって:

* **0.5% 未満の建玉は最初から見えない**
* 閾値を割った後の建玉は「その値以下のどこか」で、ゼロかもしれない
* 見えているのは常に総空売り残高の **下限**

実データでの例（3905, 2026-08-03 時点、10 年ぶん）: 24 の保有者の最新値を
単純合計すると **9.62%**。そのうち直近に更新のある報告義務中は **2 社 2.30%**
だけで、17 社は閾値割れ、5 社は解消または報告停止。足すと
**いない売り方を数えることになる**。

この理由で、DB・API・画面のどこにも `total_short_*` という名前を置かない。
`visible_*` / `reported_*` のみ。

状態は 5 つ:

| 状態 | 意味 | visible_* | reported_in_scope_* |
| --- | --- | --- | --- |
| `reporting`（新しい） | 報告義務が続いていて、直近に更新がある | **入れる** | **入れる** |
| `reporting` + `stale_reporting` | 閾値は割っていないが報告が止まっている | 入れない | **入れる** |
| `below_public_threshold` | 0.5% 割れの最終報告。実際の値は不明 | 入れない | 入れない |
| `closed` | 明示的にゼロと報告 | 入れない | 入れない |
| `unknown` | 比率が読めない行。**欠損は解消ではない** | 入れない | 入れない（件数だけ） |

### 報告が止まったもの（`stale_reporting`）

報告義務は 0.1% 動くたびに発生する。0.5% 以上の建玉が半年間 1 度も 0.1%
動かないのは実務上ほぼ無い。にもかかわらず本番データでは:

| 最終報告からの経過営業日 | 件数 |
| --- | --- |
| 0–20 | 3,035 |
| 21–60 | 271 |
| 61–125 | 69 |
| 126–250 | 37 |
| 251–500 | 148 |
| 500 超 | 792 |

分布が明確に二峰で、間が谷。**940 件（21.6%）が 250 営業日超**、685 銘柄に
またがる。3905 では ExodusPoint が 1,423 営業日前（5.6 年）の値のまま
「報告義務中」で合計に入っていた。ある銘柄では合計が 39.77% になる。

**2 口径で持つ**（第十三轮 P0-3）。125 営業日はデータ品質のヒューリスティック
であって、公式ルールに失効期限は無い —— 変動が 0.1% に届かなければ再報告
義務は生じないので、何年も動かない古い値が「まだ正しい」可能性は法的には
残る。だから:

* `visible_*` = 新鮮（125 営業日以内）な報告義務中だけの和。因子と状態判定は
  こちら（古い値を「今の圧力」と読まない）。
* `reported_in_scope_*` = 最終報告がまだ公開範囲内の全機関の和（公式口径）。
  画面には両方出す。

「割った」（below）と「割らないまま止まった」（stale）は列を分ける。境目は
谷の位置から **125 営業日**（約半年）。

株数合計は比率合計と **同じ保有者集合**で数える。株数が 1 件でも欠けたら
合計を出さない（欠損を 0 として足すと合計が黙って小さく出る）。

### 窓内の変化は「報告と報告の差」（第十三轮 P0-4）

5 日・20 日の変化は **可視合計の差では取らない**。可視合計は機関ごと出入り
するので、0.60%→0.49% の実際の −11 万株が「−60 万株」に化ける（閾値割れで
合計から機関ごと消えるため）。正しくは同一連鎖（機関 × ファンド）の隣り合う
報告の差を積み上げる: 閾値割れは「最終報告の値までの減少」、再参入は「最後に
見えていた値からの増加」、初出は開示された全量。

### 訂正の 2 段階選択（第十三轮 P0-5）

同じ (連鎖, 仓位日) の中で締切以前の最新公開版を採り、その **有効版の中で
仓位日が最新** のものを現在状態とする。1 段階（公開日最新）だと、古い仓位日の
訂正が後から公開されただけで新しい仓位状態が巻き戻る。訂正はイベントには
残るが、增仓/减仓などの **行動としては数えない**。

### 連鎖 = 機関 × ファンド

同一機関が複数ファンド名義で並行報告する行が実データに 2,094 行ある。生表の
主キーにもファンド名・住所が入っており（v8）、機関単位に潰すと片方のファンド
の建玉が黙って消える。表示は機関単位に集約（`chain_count` に内訳）。

## 3. 機関実体の正規化

3 層（v2: 剥がすのは **法人形式語だけ**。`International` / `Securities` /
`Capital` / `証券` などの営業実態語は残す —— v1 はこれも剥がしたため
`Barclays Capital Securities Ltd` が `barclays` に潰れ、モルガン・スタンレーの
英国法人と米国法人が同一実体に化けた。同じ正規化名に複数の住所が観測された
名前だけ、住所の指紋で実体を分ける）:

* `institution_legal_entity` — 法的主体。**似ているだけでは統合しない**
* `institution_group` — 表示・集計用の別レイヤー。下の行は法人のまま
* `institution_alias` — 生表記 → 法的主体。人手で維持できる

統合が起きるのは 2 通りだけ:

1. 正規化（NFKC・大小文字・記号・法人格語）で **完全一致**
2. 人手の別名表に載っている

信頼度は「統合が誤りうる場合にだけ」下げる:

| `match_kind` | 信頼度 | いつ |
| --- | --- | --- |
| `exact` | 1.0 | この実体に属する生表記が 1 つだけ（統合していない） |
| `curated` | 1.0 | 人手の別名表 |
| `normalized` | 0.75 | 正規化で別の生表記と一致した |
| `aggregate` | 0.35 | `個人` など、法人ではなく別人の集合 |

例: `モルガン・スタンレーMUFG証券株式会社`（日本）と
`Morgan Stanley & Co. International plc`（英国）は **別の法的主体**のまま、
グループ `morgan-stanley` で束ねて見られる。

`個人` は 1,863 件・133 銘柄に出るが、これは 1 つの機関ではなく複数の別人の
集合なので、1 実体として数えると機関数を誤る。

## 4. 因子

### 圧力 — 比率ではなく出来高で正規化

```
pressure_adv20 = 公開空頭株数の変化 / 20日平均出来高
```

「今回の公開空頭の変化は、平常の何日分の出来高に相当するか」。比率変化だけで
時価総額の違う銘柄を比べない。外れ値は ±5 で切り、スコアへは飽和写像で潰す
（1 社の巨大報告がスケール全体を支配しないため）。

### 吸収 — 横断面分位で決める

```
raw_damage = -min(相対TOPIX, 相対業種) / pressure_adv20
absorption = 100 - percentile(raw_damage, その日の全銘柄)
```

* 圧力が **ADV20 の 2% 未満**なら何も言わない（小さい分母で割らない）
* 相対リターンは市場対比と業種対比の **弱いほう**を採る（都合のいいほうを選ばない）
* 5 日と 20 日で向きが揃わなければ 0.7 倍
* まだ安値を更新中なら 0.4 倍（更新している限り売り圧はまだ効いている）

日本株で検証していない絶対閾値を輸入する代わりに、「その日の全銘柄の中で
どのくらいか」に置き換えている。

### 回補 と 公開可見回補天数

```
visible_covering_adv20 = max(0, -株数変化) / 20日平均出来高
visible_days_to_cover  = 公開可視の空頭株数 / 20日平均出来高
```

名前に `visible` を必ず付ける。**市場全体の回補日数ではない。**
1〜2 社に偏った減少はスコアを 0.75 倍にする（市場全体の見方の変化とは限らない）。

### 機関の入れ替わり

```
rotation = balance × volume,  balance = 2·min(in, out) / (in + out)
```

両側が動いているときだけ高い。**それ自体は強気でも弱気でもない。**

### 信用環境（リスク側）

機関空頭が多く、かつ **個人の信用買いも極端に混雑**している状態を
「踏み上げ候補」と即断しない。ここでは方向を決めず、リスク減点として扱う。

### データ信頼度

機関名の対応づけ、報告の古さ（営業日）、可視機関数、足の本数、閾値割れのみ、
訂正の有無、流動性。**古い・薄い・見えないほど下げる。リスク無しとは仮定しない。**

## 5. 状態と補助ラベル

主要状態 1 つ + 補助ラベル。「機関の入れ替わり」は吸収とも低位衝突とも同時に
起こるのでラベル側に置く。

| 状態 | 条件（要旨） |
| --- | --- |
| 挤空确认 | 公開空頭の明確な減少 + 可視回補天数 ≥ 1.0 + 突破確認 + 出来高確認 + 相対転強 **すべて** |
| 背离失效 | 空頭増加 + 長期支持割れ + 相対悪化 |
| 回补启动 | 空頭減少 + 相対転強（正式な突破は要求しない） |
| 卖压吸收 | 圧力あり + 吸収スコア高 + 安値未更新 |
| 正常做空 | 圧力あり + 吸収低 + 相対マイナス |
| 低位冲突 | 深い低位 + 新規/再参入 |
| 无动向 | 公開空頭に動きが無い |

データ信頼度が 0.35 未満のときは強い主張（挤空/吸收/回补）に落とさない。
ラベルは残す —— 何が起きたかは事実だから。

**`GATES_VALIDATED = False`。** ここの数字は初期パラメータで、
「日本株の最適値」ではない。

## 6. 評分

`institutional_short_behavior_score`（0〜100）は **研究用の並べ替え**であって
上昇確率ではない。初期重み:

```
absorption 0.30 / covering 0.22 / low_position 0.18
short_pressure 0.15 / rotation 0.08 / catalyst 0.07
```

* 欠測は **0 で埋めず重みごと外す**（「データが無い」が「悪い」に化けるのを防ぐ）
* リスク減点は最大 25 点、**順位に効く**
* `monitor_priority = score × (0.35 + 0.65 × 信頼度)` — 信頼度も順位に効く

`SCORE_VALIDATED = False`。API 応答の `validated` にそのまま出す。

## 7. 雷達との連動

**書き込み先は `alert_priority` ひとつだけ。** 最大 ±8 点、さらに信頼度を掛ける。
素の値は `alert_priority_base` として残す。

`base_quality` / `breakout_confirmation` / `intrinsic_strength` には触れない。
技術的に弱い銘柄が「機関が空売りを増やしたから」高品質の突破候補に化けるのが、
この種の連動で一番起きやすい事故なので、書き込み口を物理的に 1 か所に限る。

応答では `shadow_score` という名前で出す（`behavior_score` と同名にすると、
そのうち正式スコアとして使われる）。

## 8. 後台任務

引け後バッチの **雷達の後ろ**:

```
空売り残高同期 → 信用・業種空売り同期 → 日足同期 → 雷達スキャン
  → rebuild_events（イベント + 最後の公開状態）
  → refresh_snapshots（銘柄 × 日のスナップショット）
  → build_signals（状態が変わった銘柄だけ）
```

雷達の後ろに置くのは、突破確認と出来高確認を「挤空確認」の条件に使うから。
突破の定義は雷達 1 か所に置き、空売り側で価格を再判定しない。

* イベント ID は内容から決まるので、何度走らせても同じ行に上書きされる。
  再構築は UPSERT + **掃除**: `build_version` を全行に押し、今回導出されな
  かった旧行を最後に消す（幽霊行対策。人手の別名 curated は消さない）
* 日次スナップショットは全行 + 信号 + run マーカーを **1 トランザクション**
  で公開する。途中で落ちた半端な断面が「最新」に見えることはない。ETag は
  run_id を含むので、同じ日を訂正で作り直しても 304 に化けない
* 1 銘柄の異常で全市場を止めない（例外は握って `status: error` を返す）
* 失敗したら前回の有効なスナップショットをそのまま残す（消さない）
* API は保存済みの行を読むだけ。ページを開いても全市場計算は起きない
* **レーダー優先度連動は検証を通るまで停止**（`PRIORITY_LINK_ENABLED = False`）。
  仮の調整量は `hypothetical_priority_shift` として表示だけする

## 9. 一括配信の回填について（今回の実害）

`backfill_plan` は「計画を立てた窓の中では完了」しか意味しないのに、
ワーカー側が `pending == 0` を「履歴が揃った」と同義に扱っていた。
`backfill_years` を 1 → 10 に広げた後も、空売り残高・空売り比率・信用余額は
2025-06 起点の古い計画のまま固まり、**10 年分あるアーカイブのうち 35 / 35 / 17 本**
しか取り込めていなかった（日足だけは別の機会に立て直されて 141 本入っていた）。

対策: 計画に `bulk_history_from`（月初に丸めた窓の先頭）を残し、窓が変わったら
立て直す。取り込み済みの `bulk_done` と増分レーンの位置は保つ。

## 10. 点時セマンティクスの限界（正直に）

* 機関空売り残高は 2016-08 まで遡って **開示日つき**で入っている（140 万件）。
  ただし 2025-06 より前は月次の履歴ファイルから再構成したもので、「当時その日に
  日次配信されていたか」までは検証できない。開示日そのものは J-Quants の値なので
  点時セマンティクスは守れるが、「配信の遅れ」までは再現していない
* 業種・市場区分は現在値。過去の区分変更は再現していない
* 信用取引残高は週次。日次の混雑度は週の値を引き伸ばしている
* ニュース催化剂は現行のニュース DB 依存で、過去に遡って同じ密度では取れない
  （再生時は `has_news_feed=False` にして「無い」と扱う）

## 11. 運維

| やりたいこと | 手順 |
| --- | --- |
| 手動で作り直す | ワーカーの引け後バッチが同じ関数を呼ぶ。単発なら `pipeline.rebuild_events` → `pipeline.refresh_snapshots` |
| 履歴検証 | `python -m app.research.short_behavior_runner --start YYYY-MM-DD --end YYYY-MM-DD --out report.json` |
| 状態を見る | `GET /api/short-monitor/status` |
| 回填の進み | `sync_state` の `bulk_pending` / `bulk_done` / `bulk_history_from` |

CI は実 J-Quants に接続しない（`tests/conftest.py` のネットワーク遮断）。
実データのスモークテストは手動。
